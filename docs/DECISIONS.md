# Decisions

**Status:** Draft v0.1 · 2026-11-10

Each entry records what was decided, what was rejected and what would make us reopen it. Add a new entry rather than editing an old one; mark superseded entries.

---

## D-01 · Self-hosted, flat-price licence first

- **Decision:** Ship software the customer runs. No managed cloud until there are paying customers.
- **Why:** It is the open slot in the market, and it removes on-call duty from a one-person company.
- **Rejected:** A hosted per-seat service (competes head-on with three vendors and puts us on the critical path of every sale).
- **Cost:** Customers must run PostgreSQL and a container. Piracy is possible.
- **Revisit if:** Prospects repeatedly say they would buy only a hosted version.

## D-02 · One Rust core shared by browser, server and mobile

- **Decision:** Format decoding, hit testing, selection rules and best-available live in `cavea-core` and `cavea-format`, compiled to WASM, native server and mobile libraries.
- **Why:** The client and the server must agree exactly on orphan rules and seat adjacency. One implementation removes a class of bugs. It also gives predictable performance without garbage-collection pauses.
- **Rejected:** A TypeScript core (cannot be reused natively); separate implementations per platform.
- **Cost:** A WASM boundary to design carefully, and slower iteration on the web.

## D-03 · Web rendering on WebGL2 through `glow`, not `wgpu`

- **Decision:** The web backend calls WebGL2 directly from Rust through `glow`.
- **Why:** WebGL2 is available almost everywhere; WebGPU covered about 84% of page views in August 2026. For this workload (instanced quads) WebGPU brings no speed advantage. One published measurement put `wgpu` with its WebGL fallback at 561 KB brotli against 37 KB without it, and payload size is our main startup cost.
- **Rejected:** `wgpu` on the web; WebGPU only; Canvas 2D as the primary renderer; a general-purpose 2D library.
- **Cost:** Two GPU backends to keep in visual parity (see D-04, D-05).
- **Revisit if:** A measured `wgpu` web build with WebGL2 fits inside the payload budget.

## D-04 · Native mobile rendering through `wgpu`; WebView wrappers ship first

- **Decision:** Phase A wraps the web renderer in a WebView on each mobile platform, matching what every competitor offers. Phase B adds a native renderer using `wgpu`.
- **Why:** Customers need a mobile answer on day one. A native renderer is a genuine differentiator but is not needed to win the first customers.
- **Rejected:** Native first (delays everything); GLES on iOS (deprecated by Apple).
- **Revisit if:** Early customers do not care about native mobile; then Phase B drops in priority.

## D-05 · One WGSL shader source; GLSL generated at build time

- **Decision:** Shaders are written once in WGSL. `build.rs` uses `naga` to emit GLSL ES 3.00 for the `glow` backend. No shader translator ships to the browser.
- **Why:** Single source of truth without the size cost.
- **Risk:** Not yet proven for our shaders. Spike task `REN-002` confirms it.
- **Fallback:** Maintain the five GLSL shaders by hand, with golden-image tests guarding parity.

## D-06 · A compiled binary chart format separate from the JSON source

- **Decision:** The designer edits a JSON chart document. Publishing compiles it to CCF, a chunked binary file that the renderer decodes in a single linear pass.
- **Why:** Buyers' phones should not parse megabytes of JSON, tessellate shapes or compute labels. Compilation moves that work to publish time.
- **Rejected:** Shipping JSON; a general serialisation format (larger, and we want delta and run-length encodings tuned to rows of seats).
- **Cost:** A format to version and fuzz.

## D-07 · Parametric source model

- **Decision:** The chart document stores row blocks as parameters (rows, seats per row, pitch, curve, numbering scheme), not as individual seats. Seats are generated at compile time and in the editor's live scene.
- **Why:** It makes editing fast ("change the spacing of this block"), keeps documents small and diff-friendly, and is how venues think.
- **Cost:** Per-seat overrides need a stable identity (D-08).

## D-08 · Three identifiers per object: `oid`, `idx`, `label`

- **Decision:** A stable numeric `oid` for storage, a dense per-version `idx` for arrays and wire deltas, and a human `label` for the API.
- **Why:** Each job has a different best representation. Labels alone break when someone renames a row; indices alone break when a chart changes.
- **Rejected:** Labels as the only identifier (the leader's approach).

## D-09 · Single-writer event actor with PostgreSQL group commit

- **Decision:** Each live event's seat state is held in memory by one actor that processes commands sequentially, batches them, and commits each batch to PostgreSQL in one transaction before acknowledging.
- **Why:** Check-and-claim becomes a memory operation taking microseconds. Best-available and orphan rules need the whole event's state at once, which is awkward and slow in SQL. Sequence numbers and deltas become trivially ordered.
- **Rejected:** Row-level `INSERT … ON CONFLICT` claims (simple, but best-available needs a cached copy and retries, and a per-event sequence needs a lock anyway); Redis Lua scripts (a second required system, weaker durability).
- **Cost:** Ownership and fencing for failover; more testing effort. Mitigated by simulation testing.
- **Revisit if:** The actor's correctness cost proves higher than expected during M2. The fallback is the SQL-claims design behind the same `SeatStore` trait.

## D-10 · PostgreSQL is the only required dependency

- **Decision:** No Redis, message broker or object store is required. Compiled charts and small assets are stored in PostgreSQL; S3-compatible storage is optional.
- **Why:** Every extra system is a reason for a prospect's operations team to say no.

## D-11 · Events pin an immutable chart version

- **Decision:** Publishing creates a new version and never mutates an old one. Events move to a new version only by an explicit, validated upgrade.
- **Why:** State arrays are indexed by `idx`; immutability makes that safe and makes chart files cacheable forever.
- **Rejected:** Publish-in-place (the leader's approach, which their docs call irreversible).

## D-12 · The public sees only "available" or "unavailable"

- **Decision:** Public snapshots and deltas do not distinguish held from booked or blocked.
- **Why:** It leaks less commercial information and gives scalpers less signal.
- **Cost:** Manager views need a separate authenticated stream.

## D-13 · Commands over HTTP, state over WebSocket or SSE

- **Decision:** Holds and releases are plain HTTPS requests. Realtime connections only carry state downstream.
- **Why:** HTTP gives retries, idempotency keys, status codes and standard tooling. The realtime channel stays simple and can be replaced by SSE or polling where WebSockets are blocked.

## D-14 · Hold on select, with optimistic UI

- **Decision:** By default a tap marks the seat selected immediately and sends a hold; a failure reverts it with a message.
- **Why:** It is what buyers expect and what the incumbents do. The optimistic step keeps the tap response within one frame.
- **Alternative supported:** `session: "manual"`, where the host holds at checkout.

## D-15 · SolidJS for interface chrome

- **Decision:** The console and the designer's panels use SolidJS. All canvas drawing goes through the Rust renderer.
- **Why:** Small runtime and fine-grained updates. The chrome is not performance-critical, but the designer's inspector updates on every drag.
- **Rejected:** React (larger; acceptable, and the fallback if component availability hurts); a Rust UI framework.

## D-16 · Accessibility is a first-class feature

- **Decision:** The renderer ships a keyboard model, a live DOM proxy for the focused seat, and a full accessible list view as an alternative to the map.
- **Why:** It is a real sales argument: no competitor documents it, and customers selling in the EU have obligations for their checkout.
- **Cost:** A parallel interaction model to design and test with real screen readers.

## D-17 · No 3D

- **Decision:** No 3D venue or view-from-seat rendering.
- **Why:** Large effort, weak link to our wedge. View-from-seat photos (an image per section or seat) cover most of the value at P2.

## D-18 · Text: baked MSDF atlas plus platform rasteriser

- **Decision:** Digits and Latin letters come from a signed-distance-field atlas baked at build time. Any other text is rasterised by the platform (browser canvas, CoreText, Android canvas) into a dynamic atlas.
- **Why:** Seat numbers are the bulk of the text and must be sharp at every zoom at no runtime cost. Other scripts must work without shipping a shaping engine.

## D-19 · AI import is optional and always reviewed by a person

- **Decision:** PDF or image import produces a draft that the user corrects in the designer. It runs as an optional service; the core product works offline.
- **Why:** Detection will not be perfect. The promise is "most of the drawing done in a minute", not "no drawing".

## D-20 · Licence enforcement never blocks a sale

- **Decision:** An expired or missing licence shows a watermark and makes the console read-only. Holding and booking continue.
- **Why:** Breaking a customer's checkout over a billing lapse would be fatal to trust.

## D-21 · Main-thread rendering first, behind a command and event protocol

- **Decision:** The engine is driven only by serialisable commands and emits serialisable events. v1 runs on the main thread; a worker with `OffscreenCanvas` comes later without changing the engine.
- **Why:** A worker protects frame rate from a busy host page, but it complicates text rasterisation and the accessibility layer. The protocol keeps the option open at no cost.

## D-22 · REN-002 result: `naga` produces working GLSL ES 3.00 for the seat shader (2026-11-10)

- **Result:** D-05 holds for the `shape` program. `crates/cavea-render/build.rs` parses and validates `shaders/shape.wgsl` with `naga` 30.0.1 (features `wgsl-in` and `glsl-out` only, a build dependency) and writes GLSL ES 3.00 with `Version::Embedded { version: 300, is_webgl: true }` and no writer flags. The output compiled and linked in Chromium 157 (WebGL 2.0, ANGLE on SwiftShader, software rendering) and drew 100,000 seats with `gl.getError() == 0`. No hand-written fallback was needed.
- **What the risky features became:** `@builtin(vertex_index)` → `uint(gl_VertexID)`; `textureLoad` on a `texture_2d<f32>` → `texelFetch` on a `highp sampler2D`; `@interpolate(flat)` → `flat` varyings, including `uvec2`; `u32` and `vec2<u32>` vertex inputs → `layout(location = N) in uint`/`uvec2`, fed with `vertexAttribIPointer`; the uniform struct → a `std140` block.
- **What the backend must do because of GLSL ES 3.00:** it has no `layout(binding)`, so uniform blocks and samplers are bound by name. `naga` names each stage's block separately (`Globals_block_0Vertex`, `Globals_block_0Fragment`) and the sampler `_group_0_binding_1_vs`. `build.rs` reads these names from `naga`'s reflection output and emits them as constants, so nothing hard-codes them. Varyings are matched by `naga`'s generated names, which agree between stages.
- **Not yet proven:** the `mesh`, `glyph`, `text` and `image` programs, and a hardware GPU or another browser engine. (A Firefox headless screenshot was attempted; it is taken at the `load` event, before the WASM has started, so it proved nothing.) Revisit if one of those fails to translate.

## D-23 · The batch commit is one statement of data-modifying CTEs, not a pipelined transaction (2026-11-11)

- **Decision:** `PgStore` writes a batch (08 §4.4) as one SQL statement: the fence is an `UPDATE … RETURNING` CTE, every other part is a CTE fed by `UNNEST` arrays and gated on the fence, and the statement returns whether the fence matched. It runs outside an explicit transaction, so it is one round trip and atomic on its own.
- **Why:** 08 §4.4 asked for the eight statements in one round trip as a pipelined transaction. `sqlx` 0.9 does not pipeline: each `execute` waits for its reply, so a transaction of separate statements costs `BEGIN`, one round trip per non-empty part and `COMMIT` (5 for a one-command hold, up to 10 for a full batch). Measured locally (AMD Ryzen 9 7900X, PostgreSQL 18 in Docker on loopback, `synchronous_commit = on`, 0.08 ms round trip), both approaches commit in the same time because the WAL flush dominates: median 1.6 ms for 1 command, 3.8 ms for 100, 29 to 43 ms for 2,000. Across a real network each saved round trip is 0.2 to 1 ms per commit, which counts against the 15 ms hold budget.
- **Rejected:** a multi-statement transaction (more round trips, same atomicity); the simple-query protocol, which does pipeline several statements but takes no bind parameters, so values would have to be spliced into SQL text; a second PostgreSQL driver with pipelining (`tokio-postgres`), which duplicates `sqlx` in the build.
- **Cost:** one long statement instead of eight short ones, and a gate (`WHERE EXISTS (SELECT FROM fence)`) on every part. A refused commit costs a second query to say why.
- **Revisit if:** `sqlx` gains pipelining, or a part needs to read another part's writes (CTEs in one statement share a snapshot and cannot).

## D-24 · The server starts without an admin key; it never has a default one (2026-11-11)

- **Decision:** `CAVEA_ADMIN_KEY` is optional. When it is set it must be 32 to 512 printable ASCII characters, or the server refuses to start; when it is unset the server starts, logs a warning, and the admin endpoints (`/v1/workspaces`) refuse every request (`401`, or `403` for a valid API key, as on any admin route). Each new workspace is created with its first secret key, returned once in the creation response (08 §11).
- **Why:** 12 §4 read "required to be set explicitly". What it guards against is a default key. Requiring one at every start would make operators keep a key that can create tenants configured long after the last workspace exists; unsetting it is the safer steady state. A short key is refused because the admin key is not rate limited.
- **Revisit if:** console users and roles (09) give the operator another way to create workspaces, or an endpoint other than workspace creation needs the admin key.

## D-25 · Decoration carries its floor; strokes are built without `lyon` (2026-11-11)

- **Decision:** `TEXT`, `ICON` and `IMGS` records carry a floor, and `MESH` draw ranges are one per floor and layer, sorted (03 §4.2), so a renderer drawing one floor finds that floor's decoration. The version-1 layouts changed in place: the format was unreleased and no compiled chart existed outside tests. Strokes are convex pieces the compiler builds and fans itself (03 §3.1.1); only fills go through `lyon`.
- **Why:** Without a floor, a multi-floor chart would draw every floor's stage and labels at once. `lyon`'s stroke tessellator overlaps triangles at joins (darker joins when translucent) and its round joins use platform trigonometry; filling the union of overlapping stroke pieces with `lyon` failed its own coverage check at real coordinates (≈ 30,000 cu, where `f32` steps by 0.004 cu) because the pieces share near-collinear edges.
- **Rejected:** per-floor tables of decoration (a second index for the same thing); `lyon`'s stroke tessellator; filling the union of overlapping stroke pieces.
- **Cost:** a join whose segments are too short for it keeps butt ends and overlaps on its inner side. Only butt caps and miter or bevel joins.
- **Revisit if:** designers need round caps or joins, or dashes.

## D-26 · Compiled charts are served by content hash alone, brotli or raw (2026-11-11)

- **Decision:** The compiled chart URL is `/v1/public/charts/{hash}.ccf`, without the chart key and without a credential; the server finds the file by the public artefact's content hash, in any workspace. It stores the brotli form at publish time and serves it or the raw file; there is no gzip form. Versions are deduplicated per chart by the full artefact's hash (migration 2), so two versions that differ only in full-only data share one public file.
- **Why:** 03 §4.6 and 08 §6.2 had `/v1/public/charts/{chart_key}/versions/{hash}.ccf` under the publishable key, but chart keys are unique only within a workspace, a credential in a header defeats CDN caching and forces a CORS preflight, and a key in the URL changes the URL on every rotation. A content hash names identical bytes wherever they come from, and the file is public to every buyer of the event anyway. Every browser that runs the renderer accepts brotli, so a gzip form would add a column and a compressor for no client. The schema's `UNIQUE (chart_id, hash)` on the public hash would have refused a version that only changed oids, ranks or section priorities.
- **Revisit if:** private charts (signed URLs, P2) are built, or a supported client turns out not to accept brotli.

## D-27 · The public snapshot is re-encoded at each delta publication (2026-11-11)

- **Decision:** The actor re-encodes the public snapshot only when it publishes a delta, at the delta's `to_seq`, instead of after each commit at most every 50 ms (08 §4.5). Snapshot and deltas share one publication interval (100 ms, stretched with subscribers), with the first commit after a quiet interval published at once. Readers share the snapshot through an `Arc` swapped under a `std::sync::RwLock` instead of `ArcSwap`.
- **Why:** A DELTA is applied only by a receiver whose `seq` is its `from_seq` (08 §8.6). A snapshot taken between two delta boundaries has a `seq` no delta starts from, so a client that loads it over HTTP (or from a CDN, 08 §8.5) and then subscribes could never resume through the ring buffer and would be sent a second snapshot. Publishing both at once makes every snapshot a resume point. The snapshot is at most one interval old, and with a CDN in front it is cached for a second anyway. A lock held only to swap or clone an `Arc` costs readers tens of nanoseconds and needs no crate.
- **Rejected:** a 50 ms snapshot with 100 ms deltas, splitting deltas at each snapshot (twice the frames for every subscriber); clients applying a delta whose range contains their `seq` (it is wrong once changes the public cannot see are dropped, and changes the client rule); `arc-swap`.
- **Revisit if:** a snapshot one interval old is too stale for a use, or the read lock shows up in snapshot request latency.

## D-28 · Size gates: a committed payload baseline instead of a label; the chart corpus is pinned by hash, not compiled in CI (2026-11-11)

- **Decision:** The renderer payload gate (13 §6.3) compares the measured size with `xtask/payload-baseline.json`. Growth beyond 3% fails the build; a pull request that means it updates the file with `cargo xtask build-web --update-baseline`. A build without `wasm-opt`, or with another `wasm-opt` version than the baseline's, is refused. The synthetic corpus's compiled sizes (13 §4) are recorded in 03 §4.5 and guarded by each preset's pinned artefact hash in `cavea-testkit`'s tests, not by a CI step.
- **Why:** 13 §6.3 asked for "+3% without a justification label". A label needs a workflow that reads pull-request metadata, and the label carries no number; a committed baseline puts the new size in the diff the reviewer approves, and needs nothing beyond the existing `build-web` step. Sizes from an unoptimised build are about 20% larger and from other `wasm-opt` versions merely different, so comparing either would pass or fail by accident. 13 §4 had the corpus compiled in CI; CI builds in debug, where compiling and compressing the 100,000-seat preset takes 10 to 20 seconds, while the pinned hashes already fail on any change to a preset or to the compiler's output, which is when sizes need measuring again.
- **Rejected:** a GitHub label read by a workflow (another workflow, and no number); warning instead of failing above 3% (a warning in a passing CI run goes unread); building the CLI in release in CI for the corpus (minutes of build time).
- **Cost:** a deliberate increase needs a one-line change to a shared file, which conflicts when two such pull requests land together; the later one rebases and measures again. A corpus size regression is caught when the hashes are re-pinned, by the author, not by CI.
- **Revisit if:** the compiled sizes approach their targets, or CI gains a release build of the workspace for another reason.

## D-29 · REN-019 result: `naga` translates the `mesh` program too; section tints are vertex colours (2026-11-11)

- **Result:** D-05 and D-22 hold for the `mesh` program. `shaders/mesh.wgsl` (position `vec2<f32>` and colour `vec4<f32>` in, colour × the block's `alpha` out, premultiplied) goes through the same `build.rs` path with no change to it: `naga` 30.0.1 writes GLSL ES 3.00 that compiled and linked in Chromium 157 (ANGLE on SwiftShader, software rendering) and drew decoration and section fills with `gl.getError() == 0`. The colour input is fed from RGBA8 with a normalised `vertexAttribPointer`; indices are `u32` (`drawElements` with `UNSIGNED_INT`, core in WebGL2). The fragment stage uses no uniforms, so `naga` emits the block in the vertex stage only (`Globals_block_0Vertex`), and `build.rs` emits only that name. Both programs read one shared uniform buffer at binding point 0. No hand-written fallback was needed.
- **Section tints are written into the section outlines' vertex colours** (white in `MESH`, 03 §4.2.3) instead of a per-draw tint uniform: the active floor's outlines are one index range, so all section fills are one draw call (a stadium has about 120 sections), and no vertex attribute or texture is added. A tint change uploads that section's vertex span.
- **Still not proven:** `glyph`, `text` and `image`, and a hardware GPU or another browser engine.

## D-30 · Seats keep their stroke from 5 px, not only at the detail level (2026-11-11)

- **Decision:** A seat's stroke is drawn from 5 px on screen by its own size, the start of the seats level, as 04 §8 already said; the detail level (14 px) adds seat labels and icons, not the stroke. 04 §10's table had "flat seats, no stroke" between 5 and 14 px.
- **Why:** Unavailable seats are filled close to the background and drawn hollow by their stroke (04 §19). Without it, between 5 and 14 px, the most used zoom range, available and unavailable seats would differ by lightness alone (`11-accessibility.md` §6 asks for more than colour). A per-seat rule also handles rows whose seats are larger than the chart's default.
- **Cost:** At small sizes the 1.5 px stroke is a large share of a seat.
- **Revisit if:** a device study shows strokes at 5 to 14 px cost frame time or legibility.

## D-31 · Realtime routes take the publishable key in the URL (2026-11-11)

- **Decision:** `GET /v1/public/events/{event}/state`, `…/stream` and `/v1/public/rt` take the publishable key in the `key` query parameter instead of `Authorization` (08 §6.2, §8.2, §8.5, §11). The key names the workspace, so the snapshot URL is a complete CDN cache key; a cached snapshot may reach a page the key's origin allow-list would refuse, or outlive a revoked key by a few seconds. The hold token stays out of every URL: the WebSocket carries it inside SUBSCRIBE.
- **Why:** browsers cannot set headers on a WebSocket or an `EventSource`; event keys are unique only within a workspace, so the URL must name the workspace for a shared cache to keep one event's snapshot apart from another workspace's (D-26 had the same problem for charts); a credential in a header stops shared caching and forces a CORS preflight. A publishable key is public (it is in every page that embeds the renderer), and the public snapshot reveals only which seats are unavailable (D-12).
- **Rejected:** the key in `Authorization` with `Vary: Authorization` (most CDNs do not cache it); the workspace in the path (a workspace would come from the request, against 08 §11); the key in `Sec-WebSocket-Protocol` (WebSocket only, and misuses the header); the key in a first frame (SUBSCRIBE has no field for it, and the origin could then only be checked after the upgrade).
- **Revisit if:** private or channel-specific snapshots are built (they are `private`, 08 §8.5), or a customer needs the allow-list enforced on cached reads.

## D-32 · REN-024 result: `naga` translates the `glyph` program; ink is read from the seats' dynamic buffer (2026-11-11)

- **Result:** D-05, D-22 and D-29 hold for the `glyph` program. `shaders/glyph.wgsl` goes through the same `build.rs` path unchanged: `naga` 30.0.1 writes GLSL ES 3.00 that compiled and linked in Chromium 155 (ANGLE on SwiftShader, software rendering) and drew seat labels with `gl.getError() == 0`. New in this program and translated as expected: a second uniform block (`Font_block_1Vertex`, the glyph metrics, `array<vec4<f32>, 64>` indexed by a per-instance code), `vec4<u32>` and `vec4<i32>` vertex inputs fed from `u8` and `i8` with `vertexAttribIPointer`, dynamic indexing of a vector by the slot, `textureSample` with a sampler (a `sampler2D` in the fragment stage, on texture unit 0) beside `textureLoad` of the palette in the vertex stage (unit 1). The GL backend binds blocks and samplers by the names `build.rs` emits, the globals at binding point 0 and the metrics at 1, uploaded once at start. No hand-written fallback was needed.
- **Ink follows state through the instance's `idx`, not through the label buffer.** Each seat's label is one instance; the draw binds the label buffer from the chunk's slot and the seats' dynamic buffer (category, visual state, effects) at the chunk's first `idx`, so the program fetches the ink texel exactly as the `shape` program fetches fill and stroke (04 §8, §9). `DrawCall` gained a second texture and, per range, the label buffer instance where it starts (`bases`). A status change, a selection or a theme change uploads nothing to label buffers, and dimming applies to labels as to seats.
- **Rejected:** a colour index per glyph instance (labels rebuilt on every hold and delta); a copy of the seats' state in a texture indexed by `idx` (a second upload on every state change); per-glyph instances with the seat's attributes at a divisor of four (40 to 48 bytes a seat, over the 6 MB budget for 64 chunks of 4,096 seats); glyph metrics in each instance (the same); a third texture for the metrics (a constant uniform block needs no upload path and no texture unit).
- **Anti-aliasing:** coverage is the distance in device pixels, the atlas's range per em times the label's em on screen, computed once per label in the vertex stage. Labels are upright and scaled uniformly, so this is exact; screen-space derivatives would cost a fragment-stage computation and are coarse (2 × 2 pixel blocks) on some mobile GPUs.
- **Still not proven:** `text` and `image`, and a hardware GPU or another browser engine.

## D-33 · The glyph atlas: Roboto Condensed Medium, 40 glyphs, 16 px per em, a browser-decoded PNG baked by a pinned Nix shell (2026-11-11)

- **Decision:** The baked atlas (D-18) holds 0–9, A–Z, space, `-`, `.` and `/` of Roboto Condensed Medium 3.016 (SIL OFL 1.1), as a multi-channel signed distance field at 16 px per em with a 3 px range: a 92 × 92 PNG of 9,458 bytes. The host fetches it with the WASM and decodes it with `createImageBitmap`; the engine receives RGBA8 pixels with `SetGlyphAtlas`; the metrics are compiled into the WASM. `tools/glyph-atlas` bakes it with `msdf-atlas-gen` 1.4, built from source in a pinned `nix-shell` (nixpkgs has no MSDF generator), after removing the font's overlapping contours with fontTools; the baked files are committed and checked by a test.
- **Why:** The atlas is the largest single item in the renderer's payload (01 §5). Measured (04 §12): 256 × 256, the size first planned, is 41 KB for this set and 62 KB for printable ASCII; this set at 16 px per em is 9.5 KB and reads correctly from the 7 px minimum to about 110 px per em, the largest a label reaches (64 px seats at a ratio of 3), with small notches at the junctions of `3`, `4`, `A` and `B` from about 60 px per em; 24 px per em (16.1 KB) would remove most of them, for 6.6 KB more. Seat labels in the synthetic presets are digits only, and digits plus capitals cover nearly every seat label; lowercase and other punctuation are row-label and price text, which the dynamic atlas can draw. A PNG is the smallest form tried (raw RGB8 plus brotli was 4 to 15% larger) and needs no server configuration and no decoder in the WASM; embedding the bytes in the WASM would have delayed the first frame (04 §4). Condensed digits (0.5 em, tabular) let labels be about 9% larger in a round seat than Roboto's regular width.
- **Rejected:** a generator crate in `xtask` (the pure-Rust `fdsm` brings `nalgebra` and `image` into every CI build); a single-channel distance field (4 KB at the same size; it rounds corners under magnification, why D-18 chose a multi-channel field; not compared further); Roboto at its regular width (digits 0.568 em).
- **Cost:** No lowercase in the baked atlas. Rebaking needs Nix and a minute to build the generator. Roboto 3's licence must ship with the renderer: `packages/renderer/assets/OFL.txt` sits beside the atlas, and a product built on Cavea must carry the font's copyright and licence notice.
- **Revisit if:** seat labels with lowercase are common in real charts; the notches at high zoom are judged worth 6.6 KB (24 px per em); or the payload budget tightens enough that the atlas's 9.5 KB matters.

## D-34 · Session tokens are HS256 keyed by a secret key, verified with its stored SHA-256 (2026-11-11)

- **Decision:** A session token (08 §11) is a JWT signed with HS256; its `kid` header names one of the workspace's secret keys, and the HMAC key is that secret key. A secret key is 67 bytes, longer than SHA-256's 64-byte block, so HMAC uses its SHA-256 in its place (RFC 2104 §2): the 32 bytes the server already stores in `api_keys.hash` verify the token, and a backend can sign with the key text as any JWT library expects, or with its SHA-256. A revoked key no longer verifies; rotation is signing with the new key's id. No new secret, storage or endpoint.
- **Why:** 08 §11 had "signed by the customer's backend with a secret key (HS256)", but the server keeps only key hashes, so it could not have verified an HMAC keyed by anything it does not hold. Keying by the hash needs nothing new on either side.
- **Cost:** a stored key hash, harmless until now (a key is found by its hash, and the hash does not authenticate), becomes enough to forge session tokens if the database leaks. Accepted: session tokens gate seat holding, the anti-hoarding defence, not booking or anything a secret key does; a forged session still holds only within each token's object limit, the per-`sub` cap and the rate limits.
- **Rejected:** a separate signing secret per key or workspace, shown once like a key. Stored in the same database it leaks in the same breach, so it only helps if it is encrypted with a key kept outside the database (a KMS or a server-side key in configuration), which is new key management for every deployment. Asymmetric tokens (RS256, EdDSA) with a registered public key: safe against a leak, but a key upload and management endpoint, and the customer runs key generation.
- **Revisit if:** session tokens come to authorise more than holding (channels that gate inventory a customer sells separately, or booking), or a deployment needs a database leak not to let anyone mint sessions; then a per-workspace signing key encrypted outside the database, or asymmetric keys, with a `kid` of their own.

## D-36 · `caveaServer`: resync on the stream, lazy hold tokens, a transport that worked is kept, the clock offset in the adapter interface (2026-11-11)

- **Decision:** The renderer's server adapter (05 §4.1) resyncs by subscribing again with `seq` 0 (polling: asking from 0), so the SNAPSHOT arrives on the stream in order with the deltas after it, instead of fetching `…/state` over HTTP. In `start` mode it creates the hold token at the first tap, not on load, and replaces a token that has ended with a new one within the same hold. `auto` gives a transport up only after two consecutive failures with no HELLO ever on it, and never goes back to a better one. It reconnects SSE itself after every error, with jittered backoff, instead of leaving dropped connections to `EventSource`. The adapter context gains `setClockOffset`, and `Selection.expiresAt` is on the page's clock.
- **Why:** An HTTP snapshot can be up to six seconds old behind a cache (08 §8.5) and older than the stream's position, so the deltas after it never line up; the stream's own SNAPSHOT is in order by construction. An eager token costs every visitor who never taps a request, a server-side hold record and, with sessions, one of `max_tokens_per_sub`. A transport that once worked and then drops is a server restart or a network blip, not a blocked transport: falling back then would leave a page on polling for its life. `EventSource` retries after a fixed delay, so a restart would bring every SSE client back at once. Only the adapter knows the server's clock (HELLO, token creation), and only the map runs the expiry callbacks; a host computing a countdown from a server timestamp and `Date.now()` is wrong by the buyer's clock error.
- **Rejected:** a token created on connect (simpler first tap, the costs above); periodic retries of the better transport (flapping, and polling is rare); expiry callbacks in the adapter (every custom adapter would repeat them).
- **Revisit if:** first-tap latency matters more than the cost of idle tokens, or polling turns out to be common enough that upgrading back to a WebSocket pays.

## D-37 · The reconciler is `cavea-server verify`; the log carries a hold's limit but never its token hash (2026-11-11)

- **Decision:** The reconciler (13 §3.3) is a subcommand of the server binary, `cavea-server verify`, not `cavea verify`. `CreateHold` log rows carry the hold's object limit in `detail`, so replaying the log rebuilds every `holds` column the engine writes except `token_hash`; the reconciler verifies holds by id, expiry, limit and objects, and reports the token hash as not checked.
- **Why:** The CLI has no database driver or async runtime; adding `sqlx` and `tokio` for one subcommand would more than double its dependency tree, while the server has both, and its image is what a customer has deployed and can run after an incident with the settings it already has. The token hash is the SHA-256 of a bearer secret; `holds` keeps it only while the hold lives, but the log is kept for 400 days and exported by the reports endpoint, so logging it would spread a token's fingerprint far beyond the hold for a check that adds little: a wrong hash cannot double-book a seat, and a corrupted one makes the token unusable, which its holder notices.
- **Rejected:** `cavea verify` in the CLI (its build cost); logging the token hash (exposure for no correctness gain).
- **Cost:** operators run the reconciler through the server binary or image; a stored hash that was changed goes undetected.
- **Revisit if:** the CLI gains a database driver for another reason, or tokens need auditing after their hold ends.
## D-38 · Dynamic text crosses the engine boundary as an event and a command, not a host trait (2026-11-11)

- **Decision:** The engine asks for a string with `Event::TextRequest` (id, text, size in device pixels, weight, font family) while it builds labels, and the host answers with `Command::SetText` (id, width, height, the em it drew at, coverage bytes). The `TextRasteriser` trait of `cavea_render::host`, written for this, is removed. On the web the SDK's host draws each request on one small 2D canvas (`OffscreenCanvas` where there is one) as it takes the engine's events after a frame, and calls `View.setText`.
- **Why:** D-21: the engine is driven by commands and emits events, so it can move to a worker. A synchronous trait would be called in the middle of building a frame, so `fillText` would run between GL calls, and in a worker the canvas would have to be the worker's; with an event the host decides when and where to draw, outside the frame, and a worker host answers the same way from an `OffscreenCanvas`. Tests answer with a fake that returns fixed bitmaps, through `Engine::handle` like everything else. The cost is a frame of latency for a new string, which seat labels already accept (the atlas arrives late too), and a request id kept per pending string.
- **Bounds:** at most 16 requests a build and 64 outstanding, 4,096 strings tracked, 256 bytes a string, rasters of at most 1,024 × 512 px (the host shrinks the font to fit; larger answers are refused as `InvalidInput`). An answer to a request the atlas no longer waits for (a new chart, a new font, a cleared atlas) is ignored: request ids carry on across charts. An empty answer settles its request as "cannot draw". A host that never answers leaves those labels undrawn and the frame loop idle.
- **Rejected:** a synchronous trait (above); measuring with one call and drawing with another (two round trips for one string; the raster's size is the measurement); the browser drawing labels in a DOM overlay (01 §5 keeps overlays few and outside the frame loop, and labels must follow the camera every frame).
- **Revisit if:** worker mode (REN-P2) finds the per-request copy of the bytes costly, or a native host wants to batch.

## D-40 · The designer's views are pulled once per frame, not pushed (2026-11-11)

- **Decision:** The edit core does not push view models to the chrome (07 §2 said "pushed to the chrome when they change"). Once per animation frame the shell calls `Session::changed`, which names the views whose sources (document revisions, the selection, the validator, the guides, the tool, inputs) differ from the last call, and re-reads only those (07 §2.3).

## D-41 · TypeScript types for the designer come from our own generator over the serde attributes, not a derive crate (2026-11-11)

- **Decision:** `cargo xtask types` (`xtask/src/types.rs`) reads the Rust source with `syn`, starts from the designer's call table (`crates/cavea-designer/src/calls.rs`) and writes a TypeScript type for every type reachable from it, as serde would write it (or, for a type that only derives `Deserialize`, read it), with the call table and a class with one method per call (07 §2.4). It models `rename`, `rename_all`, `rename_all_fields`, the four enum representations (`tag`, `content`, `untagged`), `skip`, `skip_serializing_if` (an optional field, never `null`, as `exactOptionalPropertyTypes` needs), `default`, type aliases, generics, and struct templates written with `macro_rules!` (the compiler's `node!`). Anything else (`flatten`, `transparent`, `with` without an entry in its override table, a manual `Serialize`, a tuple variant tagged internally, a name defined twice) stops it with an error. It also writes the model as JSON, against which the package's boundary test checks every reply at run time. The committed output is kept current by a test in `xtask` and `cargo xtask types --check`.
- **Why:** correctness and build time. `ts-rs` 12.0.1, tried on the shapes the designer has, wrote `u64` as `bigint` (JSON gives a number), a field skipped when empty as required (`v: Array<number>`), a skipped `Option` as `?: T | null`, and the untagged `Outline` with `#[serde(with)]` as `null | Points` instead of `"auto" | Points`, warning only. A derive crate also needs a derive on every crossing type, about 40 of them in `cavea-compiler`, behind a feature in two crates, and adds `ts-rs`, `ts-rs-macros`, `thiserror`, `thiserror-impl` and `termcolor` and a `syn` 2 build with `full`. Ours adds no crate to `Cargo.lock` (`syn` 3 and `proc-macro2` were already there, under `serde_derive`), touches no library crate and builds only with `xtask`: the second build of `syn` 3 (with `full`) and `proc-macro2` (without `proc-macro`) that `xtask` needs adds 1.1 s of one core to a clean build (0.83 s and 0.31 s by `cargo build --timings`). The server and the buyer payload are unaffected.
- **Rejected:** `ts-rs` and `specta` (the above); `serde-reflection`, which traces `Deserialize` and cannot see internally tagged or untagged enums or `skip_serializing_if`; hand-written TypeScript (it drifts).
- **Reuse:** `FND-007` adds a `Target` with the buyer SDK's sources and its root types (no call table) to `TARGETS` and imports the generated file in `@cavea/renderer`.
- **Revisit if:** the shapes need a serde feature the generator would take more than a few dozen lines to model, or a maintained derive crate gets these cases right.

## D-42 · Icons are signed-distance strokes in the `shape` program, not an icon atlas (2026-11-11)

- **Decision:** The three seat icons (tick, cross, accessible) and the six decoration icons of 03 §2.7 (entrance, exit, stairs, toilets, bar, lift) are unions of round-capped strokes, 55 in all, in a constant table of `shaders/shape.wgsl`, evaluated as a signed distance in the fragment stage. Seat icons are drawn by the seats' own draw at the detail level (uniform `mode` 1), chosen per seat in the vertex stage by visual state and the accessible bit, which moves into the static buffer (`shape` bit 7). Decoration icons are `shape` instances made once per chart (`mode` 2). The 04 §6 icon atlas (256 × 256, RGB8) is not built; REN-028's "icon atlas" is met by the icons, not by an atlas.

Measured (brotli, quality 11): the strokes and their code add about 1.0 KB of shader text; the same pictograms in a 256 × 256 atlas at 85 px each are a 3,515-byte PNG (single channel; RGB8 compresses to the same), plus a fetch, a decode and a texture, and blur beyond 85 px, which a 64 px seat at a pixel ratio of 3 reaches. Seat icons inside the seats' draw cost no draw call, buffer or upload: a hold, a delta or a theme change moves them with the state already in the seats' dynamic buffer. The artwork is original (drawn from the strokes' coordinates), so there is no licence to carry; the accessible mark follows the international symbol of access.

- **Cost:** fragment work for seats with an icon at the detail level (up to 11 stroke distances a pixel), no visible change on SwiftShader. Pictograms are limited to strokes and dots.
- **Revisit if:** icons need fills or colour, a customer supplies its own pictograms (then an atlas), or a device profile shows the fragment cost.

## D-43 · Row labels come from the dynamic atlas only, and collision runs in chart units once per build (2026-11-11)

Row labels, text objects and section labels are placed greedily by priority (sections, text objects, rows; chart order within each) on a grid in chart units, once per build, not on a screen grid per frame.

Dropping it saved 1,104 B brotli and a draw call, and row labels look like the section and text labels around them. Row labels are few distinct strings (`A` to `Z`, numbers), shared across sections, so the atlas holds them cheaply. ## D-44 · GPU resources are a cache the engine rebuilds after a lost context; the host times frames, the engine counts (2026-11-11)

- **Decision:** On `ContextLost` the engine forgets every GPU resource and makes no GPU call; on `ContextRestored` the backend compiles its programs again (`GpuBackend::restore`) and the next frame makes each resource again exactly once from what the engine keeps on the CPU (scene arrays, palette bytes, the mesh with its tints, the glyph atlas's pixels); labels and the dynamic atlas rebuild as they are needed, asking the rasteriser again. The protocol's placeholder `Metrics` event and its `Mark` and `FrameStats` types are removed: the engine reads no clock, so timing marks and frame times are the SDK's (`performance.now()`), and the engine exposes only counts (`Engine::frame_stats`: draw calls, seats drawn, level, ratio), read when `onMetrics` is delivered.
- **Why:** One creation path for load and restore, and no copy of anything the GPU holds beyond what the engine already keeps (the dynamic atlas's pixels are not kept; the host draws them again). A lost context costs nothing while lost and about 0.5 ms of engine CPU on `stadium-100k` to come back. Timing at the boundary keeps the engine deterministic (§26 replay) and costs nothing when no one asks: without `onMetrics` the frame loop reads no clock.
- **Rejected:** recreating the whole view and reloading the chart (a refetch, and selection and holds would have to be replayed); keeping the dynamic atlas's pixels on the CPU (up to 4 MB for a rare event); an engine `Metrics` event fed with host times (the host already has them).
- **Revisit if:** worker mode (REN-P2) needs the statistics from inside the worker, or a backend can restore without recompiling.

## D-45 · Realtime streams run on a runtime of their own, under `SCHED_IDLE`; publications wait for the last to reach the subscribers (2026-11-11)

- **Decision:** `cavea-server` runs two Tokio runtimes, each with a worker per usable core. Requests, the actors, commits and the database stay on the first, at the default priority; every realtime connection's stream and each event's broadcast relay run on the second, whose threads set Linux's `SCHED_IDLE` policy as they start (`sched_setscheduler` through `libc`, already in the tree). The actor hands publications to the relay instead of broadcasting them itself. A publication also waits, up to 1 s, while more than 1,000 and more than a tenth of the subscribers have not taken the last one (08 §8.3). No setting: the layout is derived from the machine.
- **Why:** L1 put hold p99 at 1.25 to 1.31 s with 55,000 subscribers (13 §7.4). Per-stage timings showed it was not the database (each lookup 0.03 ms of work, commits a few ms) but queueing: every await of a hold (three lookups, the actor, the commit, the reply) waited behind a whole pass of tens of thousands of ready subscriber tasks in one run queue, about 100 ms per hop at 25,000, with the cores not even full. A second runtime took 25,000 subscribers' hold p99 from 799 ms to 112 ms; the relay removed the actor's 13 ms per publication of waking tasks on another runtime; `SCHED_IDLE` instead of nice 10 took it from 43 ms to 17 ms (nice still let fan-out threads finish their slice before a waking request thread ran). With all three, L1 measured 18 ms, the same as the 5,000 buyers alone (15 to 16 ms): hold latency no longer follows the subscriber count. Without waiting for the last publication, saturated fan-out queued publications up (delta p95 1.7 s and growing, heading for RESYNC at 64 behind); with it, they coalesce instead.
- **Cost:** delta delivery is what gives: in L1 on loopback, p95 1.1 s against 0.34 to 0.40 s before, since fanning out now gets only the cores requests leave idle, and on loopback each frame costs both ends' TCP work on the server's cores (about 4 µs of user and 10 µs of system time per frame, measured). An SSE stream's socket is still written on the request runtime (the HTTP connection owns it). A `SCHED_IDLE` thread holding a lock a request thread needs (an allocator arena, a socket's waiter list) runs again only when a core is idle; the locks shared are short, and the request runtime has no more threads than cores.
- **Rejected:** nice 10 (43 ms at 25,000); one runtime with fair yielding in long loops (each subscriber is already its own short task; the queue is the problem); a bounded set of writer threads owning shards of sockets (a rewrite of the connection loop and its guarantees for what two runtimes give); fewer, larger writes (one write per frame already, and the cost is mostly the kernel's); a setting for the thread counts (nothing yet to tune them against).
- **Revisit if:** fan-out must keep 250 ms delivery at 50,000 subscribers on 4 cores on a real network (measure there first), SSE becomes a large share of subscribers, or the server runs on a system without `SCHED_IDLE`.

## D-46 · The OpenAPI document is generated from the route table that registers the routes, with schemas held to real responses by the tests, not by a derive crate (2026-11-11)

- **Decision:** Every route is registered through `http::openapi::Routes::add` with an `Op`: its method, path, operation id, credential, parameters, request and response schemas by name, and error statuses. The router takes the method and path from it, and `openapi::document()` describes exactly the operations registered. The component schemas are written by hand in `http/openapi/schemas.rs`, every object closed (`additionalProperties: false`) with its always-present fields required. The router tests' `send` validates every response a test receives, and every JSON body the server accepted, against the schema for its route and status, with a JSON Schema check of our own over the keywords the document uses (it refuses any other keyword, so the document cannot use one it would ignore). The error codes come from `Code::ALL`. The document is committed as `crates/cavea-server/openapi.json`, printed by `cavea-server openapi`; a test fails while the file is stale.
- **Why:** "Cannot drift": a route without an entry, or an entry without a route, cannot be written; a field a handler adds, drops or retypes, or a status it starts returning, fails the tests that exercise it until the document says so. Most responses are built with `json!` (seat replies, events' counts, hold tokens), so a derive crate would have needed about 25 new structs, and its handler attributes (`#[utoipa::path(responses(..))]`) are hand-written too: statuses and shapes could still drift, and the tests would still be needed. No crate: the server stays at 194.
- **Rejected:** `utoipa` (01 §4 named it), with `utoipa-axum` to register routes: measured in a scratch crate, `utoipa` and `utoipa-gen` are two crates new to the server (its `syn` 3 and `indexmap` are already in the tree), about 3.1 s wall and 5.9 s of CPU per clean release build before any expansion, and a proc macro run over every annotated type and handler on every build of the server. A hand-written JSON file checked by tests only (two sources for every route). Deriving schemas from the serde types with a `syn`-based generator in `xtask`, as D-41 does for the designer: most bodies here have no type to read.
- **Cost:** The schemas are hand-written: a shape no test exercises is checked by nothing but review. The check covers a subset of JSON Schema. `openapi.json` is not formatted by oxfmt (it collapses short arrays; the file is serde_json's pretty form), so it is in `.oxfmtrc.json`'s ignore list.
- **Revisit if:** responses become typed structs throughout, which would let a generator read the schemas, or the subset the check covers stops being enough for a client generator.

## D-47 · The built-in interface is plain DOM under one adopted stylesheet; theme tokens are read from the computed style when something says they may have changed (2026-11-11)

- **Decision:** The web SDK's controls (05 §7) are DOM elements built by hand in the map's shadow root, styled by one constructed `CSSStyleSheet` shared by every map on the page and adopted by each shadow root, with positions, colours and the host's `theme.tokens` set through the CSSOM. Theme tokens are CSS custom properties: the controls read them with `var()` over the built-in scheme's defaults; the canvas gets them through `View.setTheme`, read from the computed style of the interface's root, colours normalised to `#rrggbbaa` by painting one pixel, and sent only when they differ from the last. They are read again on `setTheme`, at chart load, on `prefers-color-scheme` changes, on attribute changes of the container, `<html>` and `<body>` (a `MutationObserver`), and on the new `map.refreshTheme()`. The engine's `CameraChanged` carries the zoom range so the zoom buttons know the limits. Messages are an English catalogue with `{name}` placeholders and plural forms as objects keyed by `Intl.PluralRules` categories.
- **Why:** The payload is the constraint (D-28): the whole interface, prices, catalogue and token plumbing add 7.0 KB brotli, of which the stylesheet is 1.4 KB; a framework or an ICU message parser would cost more than all of it. An adopted stylesheet needs no `style-src 'unsafe-inline'`, which a `<style>` element would (05 §10). Custom properties inherit through the shadow boundary, so the DOM restyles with no script; the canvas has no such path, and CSS has no change event for a custom property. Reading on the events that do exist (theme switches by class, style or `data-*` on the root elements, and the colour scheme) covers the common cases at no cost while idle; polling, or reading per frame, would cost every idle map a style lookup per frame and break the zero-frames rule (04 §18). Painting a pixel accepts every colour syntax the browser knows (`oklch()`, `color-mix()`, names) without a colour parser in the SDK or the engine.
- **Rejected:** a style observer built on transitions of custom properties (`transition-behavior: allow-discrete`: catches every cause, but browsers differ on transitions of unregistered properties, and each change runs a transition); `@property` registration (global to the page, so two maps or the host would collide); a parser for CSS colours in the engine (bytes in the WASM for what the browser already does); ICU MessageFormat (a parser in the bundle for one plural message in four); a framework for the controls.
- **Cost:** a token changed by a stylesheet swapped in, or by a class on another ancestor, reaches the canvas only after `refreshTheme()`; the controls follow at once regardless. Browsers without constructable stylesheets (Safari before 16.4) get a `<style>` element, which a strict policy blocks. The interface is one module, so an element turned off still ships.
- **Revisit if:** a style observer becomes reliable across the supported browsers, hosts ask for tokens changed by stylesheets to apply without a call, or a separate entry point lets bundles drop elements.

## D-48 · A chart that cannot be fetched shows the error state and waits for a retry; a tap pins the tooltip, which is where ticket types are chosen (2026-11-11)

- **Decision:** With the built-in loading state on (`ui.loading`, the default), a chart fetch that fails does not reject `createSeatMap`: the error state shows with a Retry button, `chart_fetch_failed` goes to `onError` as recoverable, and the promise resolves when a retry brings the chart. Only the chart's bytes are fetched again, from a source already known; a failing adapter `chart()` or `connect` still rejects. With `ui.loading: false` it rejects as before. On touch, and with a mouse when a seat's category has several ticket types, a tap that selects one seat pins the tooltip to it at the tap; the pinned tooltip offers the ticket types, the first is the default, and each choice fires `onSelectionChange` with the object's `ticketType` and `price`. The tooltip of a long press (04 §14) is the touch path to an unselected seat's details.
- **Why:** 05 §9 asks for an error state with a retry; a rejected promise leaves no map whose state could retry, and a host awaiting `createSeatMap` would have to rebuild the map itself. Keeping the promise pending gives the buyer the retry and the host a map once it works. The adapter's `connect` and `chart` are called once by contract (05 §4), so retrying them would need every adapter to support reconnecting: out of scope here, and the chart is the fetch that usually fails alone (a CDN). Touch has no hover, so the content the tooltip carries would otherwise reach touch buyers only through a long press nobody discovers; pinning to the tap that selects gives it to them in the moment they need it, and gives a mouse buyer a tooltip they can reach to choose a ticket type without it vanishing as the pointer crosses other seats.
- **Rejected:** rejecting and leaving an error panel whose Retry builds a new map (the host keeps no handle to it); a `retry()` on the rejected `CaveaError` (new API for the same thing); retrying `connect` (above); a separate ticket-type dialog (more interface, more bytes, and focus to manage); asking the type before selecting (a step in every tap for the hosts that sell one type).
- **Cost:** while the error shows, the host has no map to destroy, and an adapter that connected keeps its connection until a retry succeeds or the page goes; a host that leaves the page meanwhile leaks it. A host that replaces the tooltip owns the ticket-type choice and has no method to report one yet. The pinned tooltip can cover controls near the seat on a small screen.
- **Revisit if:** WEB-017 adds automatic retries and an abort for `createSeatMap`, adapters gain a reconnect, or hosts with custom tooltips ask to report ticket types.

## D-49 · Uploaded images are kept in PostgreSQL, per workspace, and served to anyone by their content hash (2026-11-11)

- **Decision:** `POST /v1/assets` stores an image's bytes in `assets.bytes` (D-10), under the uploading workspace, named by the first 16 bytes of its BLAKE3. `GET /v1/public/assets/{hash}` serves any workspace's asset with that hash without a credential, CORS open, immutable. Assets are never listed or deleted in v1. The type comes from the bytes (PNG, JPEG, WebP); nothing is decoded.
- **Why:** A buyer's browser must fetch a chart's background images with the URL alone, cached by browsers and CDNs across buyers and key rotations, exactly as the compiled chart (D-26): 128 bits cannot be guessed, and the URL names neither workspace nor chart. The same bytes in two workspaces are one file served. Without delete, nothing a published version or a draft refers to can disappear; the thumbnail is an asset too. PostgreSQL first, behind two functions (`assets::put`, `assets::get`), so S3 (SRV-054) changes those two.
- **Rejected:** a credential on the image route (no CDN caching, a CORS preflight per image, and the renderer would need the key for a public file); serving a workspace's assets only to its keys (the same); a local directory (a second store to back up, and nodes would need a shared volume); decoding to check images (a decompression bomb would be the server's problem; the header's size is bounded instead); SVG (it can carry script).
- **Cost:** Anyone who has an image can learn whether a server holds it. Reference images, which only the designer uses, are as public as background images to whoever has the hash. A large image takes its size in PostgreSQL and in memory while it is uploaded or served; the node bounds both with a budget of bytes each (four of the largest image, 08 §6.2), refusing uploads and making responses wait beyond it, rather than streaming through PostgreSQL in pieces. No quota per workspace. A JPEG can carry other bytes inside its entropy-coded data, which the walk cannot check; the response headers make them inert.
- **Revisit if:** private charts (P2) need private images, workspaces need to delete images (then refuse to delete one a version refers to), or storage per workspace needs a limit.

## D-50 · Console sessions: a `__Host-` cookie, server-side rows, a CSRF token derived from the session, and no credentialed CORS (2026-11-11)

- **Decision:** A console session is a server-side row keyed by the SHA-256 of a 256-bit identifier carried in `__Host-cavea_console` (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`); 12 hours idle (renewed at most every five minutes), 7 days at most; a new one at every sign-in, all of a user's ended by a password change. Its CSRF token is the SHA-256 of a label and the identifier: stored nowhere, sent in `Cavea-Csrf-Token` on every non-safe request with the cookie, together with a same-origin check (`Sec-Fetch-Site`, else `Origin` against `Host`). The console's dev server proxies `/console/api` and `/v1` to the server, so there is no credentialed CORS at all. The session is a credential on `/console/api` only until CON-004 adds it to `/v1` with role checks.
- **Why:** A derived token needs no column and changes with every rotation. `__Host-` stops sibling subdomains from planting a session (login fixation); `Lax` keeps the cookie on top-level navigations, which only `GET` makes, and no `GET` changes anything. Server-side rows make sign-out and a password change end sessions at once.
- **Rejected:** a double-submit cookie (a second cookie and the same check); a random CSRF secret per session (a column for what a derivation gives); a signed, stateless session (no revocation); `SameSite=Strict` (a link into the console from an email would arrive signed out); CORS with credentials for the dev server (an allow-list to get wrong in production).
- **Revisit if:** the console is served from another origin than the API in production, or embed tokens (T10) need the same routes.

## D-51 · First run makes the setup owner the owner of every workspace; sign-in backs off per (account, address) and per account, never against an address the member signed in from (2026-11-11)

- **Decision:** While no user exists, each start stores a new one-hour setup token (one row) and logs a link holding it, the one secret the server logs; the setup that uses it, under the row's lock, creates the owner, makes them owner of every existing workspace (or creates the first), burns the token and signs them in. Sign-in protection is three layers, all keyed alike for existing and unknown emails: a per-address budget in the rate limiter (10 a minute); an exponential wait (1 s doubling to 15 minutes) after 5 consecutive failures of an (account, address) pair; the same after 20 failures of an account from anywhere, except for addresses that signed in to it within 30 days. Failures are forgotten after an hour. All in memory, per node. argon2id with OWASP's m = 19 MiB, t = 2, p = 1, two hashes at a time per node on blocking threads.
- **Why:** Workspaces made with the admin key before anyone could sign in need someone to run them, and the person holding the server's log is the operator. Lockouts that a stranger can trigger are a denial of service on the victim; keying the hard wait by address lets the member keep signing in from where they do while an attacker waits, and the per-account layer still slows a distributed guesser at new addresses. Two concurrent hashes bound memory at about 40 MiB and leave the request runtime's workers to holds.
- **Rejected:** logging the token at `warn` or printing it to standard error (it would bypass the log pipeline the operator reads); a token that survives restarts (a leaked old log would keep working); an account lockout after N failures (a stranger can hold it shut); CAPTCHAs (a third-party request from the console); storing failures in PostgreSQL (a write per failed attempt, which is the flood).
- **Cost:** After a restart, nothing is known: a distributed attack under way makes even the member's usual address wait (up to 15 minutes between attempts) until they have signed in once. Per node: N nodes allow N times the attempts. Workspaces created by the admin key after setup have no members until members management exists (CON-012).
- **Revisit if:** the server runs several nodes for one console, TOTP exists (it can relax the waits), or members and invitations change who owns a new workspace.

## D-52 · Keyboard focus is a seat the engine searches for in screen directions; the screen-reader proxy is an active descendant in the canvas, written alternately (2026-11-11)

- **Decision:** The map's virtual focus (11 §3) is always a seat, kept by the engine with the ring hidden or shown. An arrow moves it to the focused seat's row neighbour within 45° of the arrow's screen direction, else to the best seat of another row within 45° (lowest `along + 2 × |across|`), else to the best ahead, else nowhere (an edge); ties to the lower `idx` (`cavea_render::focus`, 04 §15, 11 §3.2). `Key` carries the DOM key into the engine, which says synchronously which keys it takes. At overview an arrow zooms the camera to the detail level on the focused seat; there is no section focus yet. For screen readers the canvas is `role="application"` with `aria-activedescendant` naming one of two `role="button"` proxies in its fallback content, written alternately, only the active one in the tree; selections are said in a polite region of their own (11 §5).
- **Why:** Screen directions are what a sighted keyboard user expects on curved, angled and staggered blocks, and the rule is precise enough to test as properties against a brute-force statement of it; preferring the row keeps → and ← walking a curved row, and excluding the own row from the cone keeps ↑ at the front row from jumping sideways. The search reuses the hit test's section and row boxes (1.2 µs on 100,000 seats) and lives in the engine, which has the positions and the camera, so it costs the SDK nothing and native SDKs get it too. One seat-level focus at every level keeps the baseline small and makes Enter select without zooming first (11 §3); focus at overview between sections is A11Y-010 with its own name pattern. 11 §5 fixes the container's role and the active-descendant pattern; screen readers announce a change of `aria-activedescendant`, not reliably a new name on the same element, hence two proxies. Fallback content of a canvas is in the accessibility tree and never drawn, so the proxies need no hiding CSS, and every id is in the map's shadow root.
- **Rejected:** a listbox with options (the spec's container is an application; a listbox implies a flat list and options screen readers count, which 100,000 seats would make meaningless); moving the page's focus to a proxy per seat (each move a DOM focus change and a blur on the canvas, and the canvas would lose its keyboard events); rows walked by `idx` alone (on rows numbered against the screen, → would go left); a k-d tree for the search (memory and code for what the existing boxes already prune); a new `MoveFocus` command (the protocol already had `Key`, and the key table belongs with the engine on every platform).
- **Cost:** the engine grew by 3.2 KB brotli (the search, the follow, `Key`); a row tilted more than 45° is walked with ↑ and ↓; a seat whose row is a single seat behind a wide aisle may be reached only by the half-plane fallback, from a diagonal. NVDA may also announce the proxy's new name when the focused seat's state changes, beside the live region: a person must check (11 §9.2). Touch screen readers cannot move between seats until the list view (A11Y-014).
- **Revisit if:** the manual checks find a screen reader that does not announce the active descendant in application mode, A11Y-010 adds section focus, or rows with steep tilts are common in real charts.

## D-53 · The start retries what may succeed later, never while hidden or offline; the host cancels with an `AbortSignal` (2026-11-11)

- **Decision:** `createSeatMap` tries the WASM, the chart (the adapter's `chart()` and the fetch), the adapter's first state (`connect`) and the glyph atlas again after a failure that may succeed later: three retries at 1, 2 and 4 s, doubling, capped at 30 s, each times 0.5 to 1.5 at random; a wait ends only when the page is shown and online. HTTP 4xx other than 408 and 429, WebAssembly that does not compile or link (or that a Content Security Policy refuses), a chart that does not decode and a browser without WebAssembly or WebGL2 are never retried. With the built-in error state, the WASM, the chart and the first state then show it with Retry (D-48 extended to all three), and while offline before the first frame it shows `offline` without Retry. A failed `connect` is called again, so an adapter's `connect` that rejects must leave nothing open. The host cancels with `options.signal`: before the map is ready, `createSeatMap` rejects with `aborted` and everything is removed; after, the map is destroyed. `preloadSeatMap` starts the WASM, the atlas and a chart early and shares them; it never rejects and keeps no failure. This replaces D-48's "a failing adapter `chart()` or `connect` still rejects" and closes its cost "while the error shows, the host has no map to destroy".
- **Why:** A failed start is mostly a network that recovers (a CDN blip, a train tunnel): retrying it quietly loads the map with no help from the buyer, and the error state is left for the failures that last. Hidden pages and offline browsers would only spend the retries, and jitter keeps a crowd of buyers from retrying in step after an outage. Retrying what cannot succeed delays the host's fallback for nothing. `AbortSignal` is the platform's way to cancel an async start, framework wrappers already hold one per mount, and it costs one option instead of returning a map handle before the map exists.
- **Rejected:** returning a handle at once with a `ready` promise (a second shape of the API for one case); retrying forever (a map that never says it failed); keeping `connect` called once (D-48's reason) and leaving a flaky first state fatal; a retry policy option (no host has asked; the constants are in one place); caching a preload failure for a time (a later map would wait for nothing).
- **Cost:** a custom adapter's `connect` may now be called again after it rejected; a start can take about 7 s more before the error state or a rejection (`ui.loading: false` rejects after the retries, not at the first failure); a host whose `assets.wasm` is a `Response` gets no useful retry (a body is read once). Bundle about +0.8 KB brotli for the error model, the retries, the signal and preload.
- **Revisit if:** hosts ask to tune the retries, the capability ladder (REN-071) changes what a failed WASM or WebGL2 means, or adapters gain an explicit reconnect.

## D-54 · The console session on `/v1`: the workspace in a header, one permission per cell of the role table, declared by every route (2026-11-11)

- **Decision:** Every route a secret key may call also takes the console session when `Authorization` is absent. The request names its workspace in `Cavea-Workspace` (`ws_…`), checked against the user's memberships in the session lookup's own query on every request (so a changed role applies to the next request), after which it is the request's workspace exactly as a key's is. Each route declares one permission in the route table (`Needs::Staff(Permission)` on `/v1`, `Needs::Member(Permission)` on the console's workspace routes, which take no API key); the router hands it to the extractor, and the OpenAPI document shows it (`x-cavea-permission`, `x-cavea-roles`). There is one permission per cell of 09 §2's table, twelve in all, some without a route yet (`channels.assign`, `reports.read`) and one checked inside the members routes (`ownership`). Read literally: an editor may not archive charts, an operator may not hold (a box-office sale books directly), and reports are the viewer's, not the editor's or operator's. Console users act with secret-key authority in the engine and appear as `usr_…`; drafts and versions record them.
- **Why:** A route cannot be added without saying who may call it, and the authorisation matrix checks every route against the role table from the same declaration, while two hand-written tables (route to permission, role to permission) hold both to the spec. Permissions as coarse as "seats.write" would have given the operator holds and the editor archiving, which 09 §2 does not. A header names the workspace without duplicating every route under a path prefix, and the scoping rule stays "the credential's workspace".
- **Rejected:** the workspace as a path segment (`/v1/workspaces/{ws}/…`, a second copy of every route); a `/console/api` proxy for every `/v1` operation (09 §10 says the console uses `/v1`); a permission check inside each handler (forgettable, and invisible to the document); caching a session's roles (a removal would outlive itself); member management with a secret key (09 lists it among the console-only endpoints).
- **Revisit if:** a role needs a permission finer than a route; the owner reads 09 §2 differently for the operator's holds or the reports; or embed tokens (T10) need the same routes.

## D-55 · The live scene is the document compiled piece by piece and merged into one chart for the buyer's engine (2026-11-11)

- **Decision:** The designer's canvas draws the floor shown as pieces, each compiled alone by the compiler (`cavea_compiler::build`: the pipeline without warnings or encoding, returning the chart as built even with errors): every top-level node outside a section; for each section its shell (no children, its outline given from the edit core's cache) and each child (inside a copy of its section with a stand-in outline). `cavea_render::live` merges them into one `cavea_format::Chart` in draw order, the pieces of a section sharing one section record and strings interned for good, and the unchanged engine draws it (`Engine::set_live`); 04 §25's "mutable `SceneSource` in which each node is a chunk" is this. Everything for the designer in `cavea-render` is behind a `designer` feature that `cavea-web` does not enable; `Scene::from_chart` repeats the tail of `Scene::decode` rather than sharing it, so the buyer's WASM stays byte for byte the same (sharing it moved the gate by 148 B).
- **Why:** Same geometry, labels and levels of detail as the buyer by construction: seat positions are the compiler's own quantised world positions, labels its rules and exceptions, sections its outline tessellation, anchor and label size, decoration its meshes; the presets compare equal to their compiled charts. The engine, culling, labels, collision, LOD and context restoration are reused whole. A piece per section child (not per top-level node) is what lets one block inside a section be re-expanded and dragged alone; the shell carries what depends on all the children (the outline, the fill, the label), which the edit core's outline cache already gives without expanding them. A lenient build keeps a node drawn while it has errors mid-edit; a node whose labels do not expand is drawn with plain numbers, as the spatial index places it.
- **Cost:** a changed node is expanded twice, once by the spatial index (positions for selection and snapping) and once by the compiler (labels, categories, flags and everything else the chart holds): the index's cache keeps positions and oids only. Measured on `stadium-100k`: compiling a 5,000-seat block 1.6 ms with its upload; the first draw compiles every piece, 75 ms natively. Each merge copies the merged arrays (about 2.6 MB at 100,000 seats, a fraction of a millisecond); uploads are limited to the pieces whose seats are new or moved. A section child's outline in the shell follows the edit core's trigonometry, which can differ from the compiler's in the last bits for a turned child. The interned strings only grow (custom label lists are copied once per compile of their node).
- **Rejected:** a `SceneSource` trait over which the engine draws node chunks directly (every engine pass, the label builder, culling and hit testing rewritten for it, and a second path in the buyer's code); building the scene from the index's expansion (the compiler's world placement, segmentation, label rules, outlines and decoration tessellation re-implemented); pieces per top-level node only (a block inside a section re-expanded with its whole section, and no way to draw it moved alone); compiling the whole chart on every edit (80 ms on `stadium-100k`).
- **Revisit if:** the compiler can take an expansion it is given, or merging shows up in a profile of large charts.

## D-56 · Chunk transforms follow the open gesture; moved pieces are baked by compiling them after it, within a frame budget (2026-11-11)

- **Decision:** The live scene decides "being dragged" from the edit core: while a gesture is open (`Editor::gesture_open`), a piece whose content is unchanged and whose placement changed is drawn with the rigid transform from where it was compiled to where it is now; pieces with one transform (a move or a turn of a selection) share draw calls. Seats, seat labels, mesh and icons take the transform in their view matrix; row labels, section labels and text objects are moved on the CPU and rebuilt. When no gesture is open, moved pieces are compiled again at their place, at most 20,000 seats a frame.
- **Why:** The edit core applies the drag's command at every pointer move (07 §9), so placement revisions change per move; turning a placement-only change into a matrix keeps a drag step free of expansion and seat uploads (0.08 ms of engine CPU for a 5,000-seat block, 0.6 ms for 100,000 seats, natively). Baking by compiling again gives exactly what a fresh compile gives (the property test compares them); transforming the compiled positions instead would round twice and drift from it. A budget keeps the frame after releasing 100,000 seats under about 12 ms.
- **Cost:** during a turn, seat labels and icons turn with their piece until it is baked (seat labels drawn from the dynamic atlas, longer than four glyphs or outside the baked atlas, are moved on the CPU with the text labels and stay upright); a section's automatic outline in its fill waits for the bake when a child is dragged (the overlay's outline follows at once).
- **Rejected:** uploading moved positions per pointer move (5,000 seats at 12 bytes a step; 1.2 MB for everything); drawing every piece with its own matrix always (one draw per piece: hundreds at overview instead of 6); detecting drags from pointer input in the canvas (the edit core already knows).

## D-57 · The overlay batcher tessellates on the CPU for the `mesh` and `text` programs; no shader is added (2026-11-11)

- **Decision:** The overlay is shapes in chart units with sizes in CSS pixels, tessellated on the CPU into triangles in CSS pixels with a one-device-pixel alpha fringe on every edge, drawn by the existing `mesh` program in one call with a screen matrix; its readouts are `text` instances from the dynamic atlas. It is rebuilt when the shapes, the view or the atlas change; polylines are simplified to half a device pixel first and segments outside the canvas left out.
- **Why:** No shader, pipeline or GL code to add to the module or translate with `naga`; edges are smooth at ratios 1, 2 and 3 without multisampling (the context has `antialias: false`); colours are per vertex, so markers, guides and the selection take any token. Measured natively with everything on `stadium-100k` selected (436 shapes, 51,073 triangles): 2.1 ms to build.
- **Cost:** a pan or zoom rebuilds the overlay (it is in screen space), and a drag uploads it every step (640 KB a step with all 180 sections' dashed outlines, 4 KB for one block); joins are covered by square caps rather than mitred.
- **Rejected:** a line program expanding segments in the vertex stage (a new shader and pipeline for a few hundred shapes); drawing handles with the `shape` program (its colours come from the palette texture, which has no overlay rows).

## D-58 · The published package is the `dist/` a build script writes, with the WASM and atlas beside one bundle; the script-tag build finds them from its own URL and pins them by hash; compatibility fixtures live outside the workspace (2026-11-11)

- **Decision:** `bun run build` in `packages/renderer` (`build.ts`) writes `dist/`: `index.js` (one ES module bundled by `Bun.build`, not minified, `process.env.NODE_ENV` left in), the declarations `tsc` emits that `index.d.ts` reaches (imports rewritten from `.ts` to `.js`), `cavea.min.js`, `cavea_web_bg.wasm`, `glyphs.png` and a `package.json` made from the source one; `dist/` is the package (`bun pm pack` in it). - **Cost:** Rollup and esbuild users copy two files (05 §13). `cavea.min.js` is 25.9 KB brotli against the 25.5 KB the payload gate measures for the tree-shaken bundle (the global object keeps every export, plus the wrapper and the hashes). A host that rewrites the atlas (an image optimiser) breaks the script-tag build's pin, and must use `index.js`. The fixtures need the network the first time and Docker for `csp-server`.
- **Revisit if:** Rollup or esbuild start copying `new URL` assets, a framework needs a different module format, or the release pipeline (OPS-001) publishes from somewhere else.

## D-59 · `@cavea/react` creates the map a microtask after mount, applies three props through setters, calls callbacks through the latest props, and recreates only for a new adapter or chart (2026-11-11)

- **Decision:** `<SeatMap>` renders an empty `<div>` and creates the map in an effect, after a `queueMicrotask`; unmounting aborts the map's `signal` (destroying a ready map, cancelling a loading one). `pricing`, `theme` and `locale` are compared as data after each render and sent to their setters; other options warn in development when they change and apply at the next creation. - **Revisit if:** the renderer gains setters for more options, adapters become reconnectable, or React changes how Strict Mode replays effects.

## D-61 · Invitations are one-time links handed on by whoever invites; the audit log is written in each action's transaction and kept (2026-11-11)

- **Decision:** An owner or admin (an owner for an owner) invites an email with a role and gets a link, `/console/invite#token=…`, once: 256 random bits, stored as SHA-256, 7 days, deleted when accepted (so a race has one winner), revoked or replaced. Nothing is sent. Signed in as that email, the user joins; with no account, they set a password and are created and signed in; any wrong, used, revoked or expired token answers the same `401` after one query. The admin key can invite a workspace's owner, which closes D-51's gap. Sensitive actions (09 §7) write one `audit_log` row in their own transaction, identifiers only; failed sign-ins only for existing accounts, written after the reply is decided; seat commands stay the event log's; rows are kept, read a page per index.
- **Why:** The server sends no email (12 §5 keeps emails out of everything but the account), and the person inviting already talks to the invitee. Writing the row with the action means the log cannot claim what did not happen or miss what did. A failure row for an unknown email is a write anyone controls at any rate; for an account, the per-account back-off bounds it, and writing it off the reply's path keeps the account's existence out of the timing. Human-paced actions make a log that grows slowly, so keeping it costs little and an index keeps it fast.

- **Cost:** A link forwarded to the wrong person makes them a member: the inviter must hand it over with care, and can revoke it. The invited email is not verified: whoever holds the link chooses the password. Audit rows grow without bound, about a hundred bytes each.
- **Revisit if:** the server gains email, SSO arrives (invitations by domain), or an operator needs the log trimmed (a `CAVEA_AUDIT_RETENTION_DAYS` beside SRV-040).

## D-62 · The console is compiled into the server from a table built before compiling, and served as the router's fallback (2026-11-11)

## D-67 · The console's Content Security Policy is strict for scripts and allows `style` attributes (2026-11-11)

- **Decision:** The console's pages and files are served with `script-src 'self' 'wasm-unsafe-eval'` (no `'unsafe-inline'`, no `'unsafe-eval'`, no other origin), `style-src 'self'` for stylesheets and `<style>` elements, and `style-src-attr 'unsafe-inline'` for `style` attributes; everything else from the origin alone, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'`. ## D-68 · The basic event manager is the picker on a console adapter that polls the staff routes, any seat selectable (2026-11-11)

- **Decision:** CON-008 builds the event manager on what exists, with no SDK change: `@cavea/renderer` in `picker` mode with a `customState` adapter of the console's own. The adapter draws a seat unavailable when it is not free and not selected, so a seat the operator selects is drawn available whatever its status; a click on an unavailable seat (the picker's `not_free` refusal) draws it available and selects it. True statuses are shown where the picker cannot draw them: the tooltip, the selection list, the details and the counts. The staff routes take the console session already and carry the domain statuses, order references and hold expiries the details need. A whole read is not one snapshot: a seat that moves between two statuses while they are paged can be missed until the next read. Polling costs one request every 3 s per open manager, plus the whole reads.
- **Revisit if:** the manager stream (SRV-039) or a manager snapshot with `after_seq` deltas lands (replace the polling); the renderer gains `manager` mode (CON-020: draw the statuses, drop the available-while-selected trick).

## D-69 · A server draft saves itself, stops at a conflict until the person chooses, and keeps unsaved work in the browser (2026-11-11)

- **Decision:** The designer saves a server draft two seconds after the last change with `If-Match` of the etag it was given, one save at a time. A `409 version_conflict` stops saving until the person chooses: keep their own (saved with the etag the conflict reported, never `If-Match: *`), open the server's (their own discarded; a download is offered first), or download their own. The chart's workspace is in the designer's address and named by every request.

Saving with `*`, or retrying a conflict with the new etag automatically, would make the last writer win unseen; stopping and asking keeps both sides recoverable. The workspace in the address keeps a link meaning one chart for everyone, and a selection changed in another tab from redirecting a save.

## D-70 · Background images are asked for with an event after the first frame and uploaded from the host's decoded bitmap; 16 images and 16 MiB a floor (2026-11-11)

- **Decision:** After a frame is drawn the engine emits `ImageRequest` (id, the asset's content hash, the longest side and the pixels allowed) for each background image of the floor shown not yet loaded or asked for: the first 16 of `IMGS` on that floor, valid hashes only. The host (the SDK's `images.ts`) fetches the URL that `assets.image` or the adapter's `image(hash)` gives (`caveaServer`: `/v1/public/assets/{hash}`), at most two at a time, decodes it with `createImageBitmap`, scales it down to the limits keeping its aspect, and hands the bitmap to `View.setImage`, which calls `Engine::set_image`; the `glow` backend uploads it with `texImage2D` from the bitmap, which the host decoded premultiplied (WebGL ignores its unpack settings for an `ImageBitmap`), through `web_sys` so a refused bitmap is an error, not a panic. `GpuBackend` gains an associated `Image` type for this. Limits: 4,096 px a side or the device's `MAX_TEXTURE_SIZE`, and 4,194,304 px (16 MiB as RGBA8) for the floor's images together, shared equally in the requests and checked again on arrival; over them an image is refused. Textures are keyed by hash, kept across a chart reload or a live-scene update for assets still shown, freed otherwise, forgotten on a lost context and asked for again after the restore. A failed image is reported (`image_failed`) and not asked for again until another chart loads. `04-renderer.md`'s `ImageSource` trait is removed.
- **Why:** Images must never delay the map, so the request follows a frame and the SDK's start never waits on it. Uploading from the bitmap keeps up to 16 MiB of pixels out of the WASM's memory, which never shrinks once grown, and needs no copy kept for a lost context: the asset is immutable and the browser's cache serves the second fetch. An event like `TextRequest` (D-38) keeps the engine free of I/O and of host calls, and the trace and test hosts answer it with a fake. Fetching with `fetch()` keeps images under `connect-src`, which every set-up already allows for the chart's origin, rather than adding `img-src`. Caps on count and memory make a hostile `IMGS` cost at most 16 requests and 16 draws.
- **Rejected:** an `ImageSource` trait the engine calls (a host call inside the engine, the protocol's one exception, and no easier to fake); passing RGBA bytes in a command (16 MiB through the WASM's heap, kept for context loss, and a `getImageData` pass); a decoder crate in the WASM (bytes, and a decoder exposed to hostile files); an `<img>` element (`img-src`, and its decode is not cancellable); mipmaps (a third more memory for a background seen mostly at one zoom).
- **Cost:** About 2.7 KB brotli of WASM (the program, the upload path, the image state) and 0.5 KB of SDK. The host's answer is the protocol's one method rather than a command (`Engine::set_image`), since an `ImageBitmap` is not plain data. After a lost context images are fetched again (from the cache), and appear a moment after the rest. A slow image server delays only that image. Large images minified at overview without mipmaps may shimmer while panning.
- **Revisit if:** charts need more than 16 images on a floor, a floor selector (WEB-030) wants other floors' images preloaded, or the Canvas 2D fallback (REN-070) needs the bitmaps kept.

## D-71 · The buyer SDK's engine types are generated from test-only Rust mirrors tied to the protocol by exhaustive conversions; the WASM's JSON stays hand-written (2026-11-11)

- **Decision:** `crates/cavea-web/src/schema.rs`, compiled for tests only, defines with serde derives and attributes the JSON the WASM writes (`EngineEvent`, internally tagged by `type`; `ObjectInfo`, `ChartInfo` and its parts; `ObjectDetails` for `View.object`) and the option names the SDK passes in (`ThemeName`, `GestureHandling`, `Lod`). `cargo xtask types` reads it as a second target of D-41's generator (roots, no call table, no schema file) and writes `packages/renderer/src/generated/engine.ts`, which `events.ts`, `text.ts`, `images.ts`, `options.ts`, `host.ts` and `seatmap.ts` use instead of their hand-written types. ## D-72 · Staff read an event's state by polling manager frames over HTTP; each commit keeps the event's count per status (2026-11-11)

- **Decision:** `GET /v1/events/{event}/state?after_seq=` gives staff (a secret key or a console session that may read events) the realtime frames of 08 §8 in domain statuses: the manager SNAPSHOT, or one manager DELTA after their `seq`, or `204`. ## D-73 · The designer's editing lock is a lease on the chart row, held by the caller's identity, enforced on saving and publishing (2026-11-11)

- **Decision:** `charts` holds one lock: holder (`usr_…` or `key_…`), since and expiry, by the database's clock. `POST /v1/charts/{chart}/lock` takes a free or expired lock, renews the caller's (60 s, renewed every 20 s by the designer), or with `take_over` takes another's; otherwise `409 chart_locked` naming the holder (with an email for those who may edit charts, while the holder is a member). `DELETE` releases one's own. - **Revisit if:** real-time co-editing is planned, embed tokens (T10) edit charts (the lock's holder would be the embedding customer's user), or people need to see a lock's history.

## D-74 · A placed picture is named by its content hash in the browser and placed at once; saves wait for its upload (2026-11-11)

- **Decision:** The image tool checks a picked file as the server will (bytes, type by signature, sides as declared and as decoded), computes its content hash in the designer's module with the server's own function (the first 16 bytes of BLAKE3), and creates the image node at once with that hash, drawn from the file kept in the page. The upload (`POST /v1/assets`) runs in the background, once per hash, retried like a save when it gets no answer. A draft save first waits for the uploads and reports *offline* (or *signed out*) while one waits, so the save machine keeps the draft in the browser and the server never holds a draft naming a picture it lacks. An upload the server refuses removes the nodes naming that picture as one undo step. A local chart file keeps the picture for the page only and says so; the file names it by hash.
- **Why:** Placing must never wait for the network, and a node created only after the upload would need a second, unsaved picture on the canvas (or a placeholder) while it runs, and could not be moved meanwhile. With the hash known before the upload, the node is final from the start: undo, redo, moves and saves need no rewrite when the upload ends, and since assets are immutable and never deleted (D-49) an undone placement leaves nothing to clean up. Holding saves behind uploads is the one place the invariant can be kept, and it reuses the save machine's offline and recovery states rather than adding a second indicator of unsaved work. The browser already decodes the file to check it, so no decoder is added; BLAKE3 is already in the module through the compiler.
- **Rejected:** creating the node after the upload succeeds (a placeholder layer outside the document, a picture that cannot be edited while it uploads, and a second undo story); naming the node by a temporary key rewritten on success (every undo entry holding the key would need rewriting); embedding the bytes in the chart document (03: assets are referenced by hash; a draft would grow by megabytes and the compiler would hold images); refusing images in local files (tracing a floor plan is the main use, and a session-only picture costs nothing to keep).
- **Cost:** A draft cannot be saved while a picture waits to upload, even if the edit was elsewhere; the work stays in the browser's store as during any outage. A tab closed before an upload loses the picture's bytes (they are not kept in IndexedDB): the recovered draft names a picture the server lacks, which is not drawn until the same file is placed again. A refusal the browser could not foresee removes a node the person placed. A local file reopened shows no pictures.
- **Revisit if:** the server takes a draft that names missing assets as a validation finding rather than an error, IndexedDB should keep pending uploads across a crash, or a picture library per workspace lets the designer pick an asset already uploaded.

## D-75 · User guides are kept in the browser, per person, workspace and chart, until the server offers editor state (2026-11-11)

- **Decision:** The shell stores a server chart's guides (`saved_guides()`) in local storage under `cavea.designer.guides.v1/<usr>/<ws>/<chart key>`, written at most twice a second and when the editor closes, and restores them into each new session of the chart. A local chart file's guides last as long as the page.
- **Why:** Guides are editor state, not chart data (07 §5.2), and the draft route takes a chart document and nothing else (03 §2 refuses unknown fields), so carrying them with the draft would need a schema change or a server change; neither is this slice's. Local storage is synchronous, survives reloads and a recovered draft, and a few guides are a few hundred bytes.
- **Rejected:** a field in the chart document (schema 2, and guides would be published); the IndexedDB safety net's record (it is removed once the server holds the draft); session-only guides for server charts (lost on every reload).
- **Cost:** Guides do not follow the person to another browser, nor reach a colleague editing the same chart; clearing site data loses them.
- **Revisit if:** the server offers editor state beside the draft (`GET`/`PUT /v1/charts/{chart}/editor-state`, a small JSON object per chart, last writer wins): then guides move there, read once when the chart opens.

## D-76 · One end-to-end check drives the first path in the flake's Chromium over the DevTools protocol, against the production build, before filing (2026-11-12)

- **Decision:** The product's first path (setup, draw, publish, event, keys, two buyers, the manager, a member, a restart, the log) is one committed check, `cargo xtask e2e` (`tools/e2e/`, 13 §9.1), run by the author before filing a change to the console, the designer, the server's routes or the SDK, never in CI. It always builds what a release ships (the server with the console compiled in, the renderer's package) and runs it on a database of its own, in the golden images' pinned Chromium (headless, SwiftShader), over the DevTools protocol with a driver shared with the golden images and the compatibility checks (`tools/chromium.ts`). It finds elements by role and accessible name in the browser's accessibility tree, acts with real pointer and key events, waits only on named conditions, and asserts on what a person would see, the SDK's reports and the server's answers; every page must report no error, policy violation or unexpected failed request, and the server's log no secret. This replaces D-60's "there is no flow suite"; its choice of no test framework stands.
- **Why:** Every screen was proven once by the builder who wrote it, with a script that was not kept, and CI runs no tests: nothing re-checked a screen after a later change, and nobody had run the whole path at once. One run of about 20 s after the build is cheap enough to ask of every such change. The accessibility tree is what a person using assistive technology gets, so finding by role and name also catches an unnamed control, and it does not break when classes or layout change. The production build is what ships: the console under its strict policy, the WASM optimised. The pinned browser makes a failure reproducible on another machine of the same flake.
- **Rejected:** Playwright (D-60: browsers downloaded outside the flake, and a framework CI would not run); the dev server (not the CSP, the build or the embedding that ship); a check per screen (the path between screens is what was never run); a reused binary checked against the tree's times (a wrong verdict would test a stale build silently; the rebuild costs about 70 s with nothing changed); pixel comparisons of the canvases (the golden images do that, deterministically).
- **Cost:** About 70 s of build and 20 s of run, a database, two ports and a browser for each run; `tools/e2e/steps.ts` moves with the screens it drives (a renamed control fails it until the step follows). One engine, software rendering, one machine: no other browser, GPU, phone or load.
- **Revisit if:** CI starts running tests (this is the first to run there), a second browser engine is needed, or the run grows past about a minute.
## D-77 · The server SDK is a generated operation table under one hand-written request layer, retried only where a repeat cannot act twice (2026-11-11)

- **Decision:** `@cavea/server-sdk` (05 §15) takes its types and a table of the operations a secret key or the admin key may call (method, path, credential, whether it takes an `Idempotency-Key`, whether it is a page) from the committed OpenAPI document, through the console's generator in `xtask/src/api.rs` (D-60), checked by `cargo xtask types --check`. One hand-written request layer applies the API's rules once for every operation: the credential in `Authorization`, path encoding, an idempotency key per logical call reused across its retries, timeouts, `AbortSignal`, problem+json into one `CaveaError`. A thin layer groups the operations by resource, with what the table cannot say (a draft's `ETag`, `If-Match`, `201` against `200`, pages as iterators); a map typed against the table makes a new operation fail the type check until it has a method or is marked raw-only. Retries happen only for reads, `DELETE`s (idempotent by the API), a draft saved over `*` and calls carrying an idempotency key, after a network failure, a timeout, `429` or `5xx`, honouring `Retry-After`. Session tokens are signed in the SDK with Web Crypto. The error message never carries the server's free text.
- **Why:** The document is ours and regular, and the generator already reads it and refuses what it does not model; a second generator, or a code-generation package, would be a dependency for the same work. A table plus one layer means a rule (the idempotency key, the retry rule) is written once and covers operations added later, and the low-level `call` reaches a new operation the moment the types are regenerated. Retrying a `POST` without a key after a lost reply could hold, create or publish twice; a draft saved over an etag would conflict with its own first attempt. The server's message for a refused body can quote the body (serde's text), and customers log errors.
- **Rejected:** `openapi-typescript` with `openapi-fetch`, or `orval` (dependencies, and they generate the rules no better than one layer does); a generated method per operation with no hand-written layer (the draft's etag, pages and created-or-existing replies need code anyway, and generated names read worse than `cavea.events.hold`); retrying every `5xx` (a `503` from a commit that failed after the fact is ambiguous for a call without a key); a key per attempt (a lost reply would be applied twice).
- **Cost:** The resource layer is hand-written: a new operation needs a line in `wrappers.ts` (the type check says so) and, to be ergonomic, a method. A new error code needs a line in `errors.ts`'s table (typed against the document). Reasons are untyped strings until the document enumerates them.
- **Revisit if:** the API grows past what one person can wrap by hand, or the document gains a reason catalogue, links between operations or other structure worth generating from.

## D-76 · The designer renews its lock only while the page is in use, and the last tab of a person releases it (2026-11-11)

- **Decision:** The save machine owns the lock's renewal (every 20 s on its injected clock) while the page is visible or has changes to save, stops when hidden and idle, and renews at once when shown, back from the back-forward cache or online. A renewal or a save answered `chart_locked` stops saving and keeps the work in the store, as a conflict does; a renewal answered with a new `since` (the lock had lapsed and was taken again) has the draft's etag checked, a changed draft being the conflict path. On `pagehide`, and on leaving the designer for another console page, the lock is released only when no other tab of the same person, workspace and chart says it holds it (a `BroadcastChannel`); otherwise it is left to that tab.
- **Why:** The lock is coordination; the etag is the guard (D-73). Putting the lock's events into the machine that keeps the save invariant, rather than a timer beside it, lets one property test cover them together. A hidden tab renewing for ever would lock a chart against everyone for as long as a browser stays open; with unsaved work it keeps renewing until that work is saved. The server sees two tabs of one person as one holder, so a `DELETE` from one would free the lock under the other; tabs telling each other is the only way to know, and a tab that dies silently costs at most the lease's minute, never a lock freed under a live editor.
- **Rejected:** Renewing from a separate timer in the page (two clocks, and the save machine would not know the lock was lost until its next save); renewing whatever the page's visibility (a forgotten tab holds the chart indefinitely); releasing on every `pagehide` (closing one of two tabs frees the lock the other uses); a Web Lock per chart held by the editing tabs (`navigator.locks.query()` is asynchronous, and `pagehide` must decide at once, before the page is frozen).
- **Cost:** A person who leaves a visible, idle tab open keeps the chart (take-over is the answer). A tab that crashed keeps its siblings from releasing: the last of them leaves the lock to lapse. A browser without `BroadcastChannel` treats every tab as alone.
- **Revisit if:** the server distinguishes tabs (a lock token per editor, rejected in D-73), or real-time co-editing replaces the lock.

## D-77 · A version's thumbnail is the designer's canvas drawing the buyer's view on a canvas of its own (2026-11-11)

- **Decision:** After a publish, the designer draws the thumbnail with its own WebGL canvas code (`@cavea/designer-core`'s `Canvas`) on a separate small canvas created with `preserveDrawingBuffer`, in a *buyer's view* (`Canvas.showBuyer`): the live scene without the overlay and without reference images, its pieces taken from the editor's canvas (`LiveSync::for_buyer`, strings interned again for the new scene), light theme, 480 × 360 px, encoded in the browser as WebP or PNG, uploaded as an asset and attached to the version. Failure is a quiet note; the publish never waits for it.
- **Why:** The live scene is the compiled chart as the buyer's engine draws it (the canvas's scenes are tested equal to the buyer's, 04 §25), so the picture is the buyer's at the cost of a merge, not a compile: about 20 ms on `stadium-100k` against 55 ms compiling again, and nothing at all on the editor's canvas, whose view, selection and frames are untouched. A canvas of its own can keep its drawing buffer for `toBlob` without slowing every frame of the editor's. Excluding the overlay and reference images is a flag in the painter, tested on the recording backend.
- **Rejected:** Drawing on the editor's canvas at a fitted view and back in one task (it would show the reference images unless the scene were merged twice, change the theme in dark mode, and depend on the drawing buffer surviving until read); the buyer's renderer (`createSeatMap`) off screen (its WebAssembly loaded for a picture, its own compile of the chart, and no way to read its canvas at a known moment without changing `packages/renderer`); rendering on the server (no GPU or rasteriser there, and a new dependency).
- **Cost:** The thumbnail shows the floor on screen when publishing. Once the person has edited after saving for the publish (a large chart compiles for seconds), the picture needs a session of the published draft, opened and compiled for it (about 55 ms more on `stadium-100k`). A publish from outside the designer (the API) makes no thumbnail. On a software rasteriser the fitted draw of 100,000 seats is one task of about 70 ms.
- **Revisit if:** the server renders charts (a headless renderer), versions get a picture per floor, or the thumbnail should show sample sales.
